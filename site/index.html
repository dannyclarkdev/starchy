Responsive layout testing, one command

Keep your layout crisp at every width.

starchy finds every screen width where your page's layout changes, and flags the changes that are bugs.

npx starchy https://example.com

Breakpoint screenshots miss the bugs in between.

Most responsive tests screenshot a few fixed widths, such as 375, 768 and 1440. A bug that only shows at 912px slips through. starchy checks the whole range, so the page itself shows where its layout changes.

How it works

starchy runs your page in headless Chromium through Playwright and sweeps it from wide to narrow.

  1. Fingerprint

    Load at 1920px. Record how each container's children sit in rows (for example 3+3+1), which elements show, and any problems.

  2. Sweep

    Step down 8px at a time. When the fingerprint changes, binary-search to the exact pixel.

  3. Capture

    Take before and after screenshots with the changed elements outlined.

  4. Classify

    Sort each change as a media query, a fluid change or a problem.

  5. Report

    Write report.html and a fingerprint.json to compare against later.

Media query

The width matches an @media breakpoint in your CSS. The change is expected.

Fluid change

The layout changed with no media query, from flex-wrap, auto-fit or content size. Check that you meant it.

Problem

Something broke at this width.

What counts as a problem

Every problem comes with the exact width range where it happens and the element that causes it.

  • Horizontal scroll

    The page is wider than the screen. starchy names the element that causes it: it hides each candidate and checks if the scroll width shrinks.

  • Overlap

    In-flow sibling elements overlap each other.

  • Escapes container

    An element sticks out of its parent's box.

  • Clipped text

    Text is cut off by overflow: hidden.

  • Wrapped link

    A link or button label of 5 words or fewer breaks onto 2 or more lines.

  • Tiny text

    Text is smaller than --min-font, 12px by default.

Catch layout regressions in CI

Save a fingerprint of a known-good build. On every pull request, compare against it and fail on new problems.

  • The comparison is structural, not pixel-based, so font rendering noise does not make it flaky.
  • The report lists new problems, fixed problems, and layout changes that appeared or disappeared.
  • Check one page, several pages, or a whole sitemap.xml in one report.
# once, on a known-good build
starchy https://staging.example.com --out baseline

# on every pull request
starchy https://staging.example.com \
  --baseline baseline/fingerprint.json \
  --fail-on new
